# Testing in the VM

`modules/vm.nix` defines a `virtualisation.vmVariant` of the laptop config: the same system and home config, booting straight into Hyprland as isaiah. The guest mounts the host's Nix store read-only (nothing is copied) and shares a checkout read-only at `~/nixos-config`, so the Quickshell symlink resolves and QML edits are visible in the guest immediately. The host toplevel is unaffected by anything in that module.

The scripts referred to below live in `.claude/skills/vm-test/scripts/` of whichever checkout you're working in; run them by that path (`$S` below is short for it). They talk to the guest through the `vm` entry in `~/.ssh/config` (port 2222, key `~/.ssh/nixos-vm`). Guest sudo password is `isaiah`.

## When to use it

Use it for changes that would disrupt the user to test on the host while they're working on it: anything Quickshell (the host's bar reads the main checkout, not your worktree), running Hyprland config changes (activating on the host needs root and a switch), and tests that drive pointer or keyboard input or depend on which workspace is showing. Nix changes that need to be run to be trusted go here too. Don't use it for a simple Nix change that doesn't involve the shell and that you're reasonably confident will work the first time, or for a test that only opens a window: those run on the host (the Checking changes section of CLAUDE.md says how).

Run everything from this session's worktree (CLAUDE.md, Git workflow): `vm-up` shares the tree it's run from into the guest.

## Sharing the VM between sessions

There is one VM (one disk image, one ssh port), and the user may have several Claude sessions running, each in its own worktree. A claim file records which worktree's session is using the VM or is about to; `vm-claim` reads and writes it.

- Before doing anything with the VM, including planning work around it, run `$S/vm-claim`. It shows the claim (worktree, branch, what for, since when), whether QEMU is running and which tree it shares, and the Claude processes on the machine with their working directories.
- If nobody holds the claim and no QEMU is running, take it straight away with `$S/vm-claim take '<what for>'`, before building, so another session sees it while you build. `vm-up` takes it too if you forget.
- If another worktree holds the claim, or a QEMU is running that shares another tree, the VM is someone else's: don't `vm-down`, `vm-switch`, `vm-qs restart` or drive input in it. Tell the user who holds it and ask whether to wait, or whether that session is finished and you can take it over. The claim lives in `$XDG_RUNTIME_DIR`, so a reboot clears it, but a session that ended without releasing leaves one behind: the user decides when it's stale. Only on their word, run `$S/vm-claim --force-release` (and `vm-down` if a guest is still up), then claim it yourself. Other local sessions can also show up in the `ListAgents` tool; if the holder is listed there you can ask it directly with `SendMessage` whether it still needs the VM.
- `vm-up` and `vm-down` refuse to act while another worktree holds the claim. `vm-down` drops your claim once the guest is off. When you're done with the VM for the task, `vm-down` (or `$S/vm-claim release` if you never booted it), so the next session doesn't have to ask.
- Landing a branch with QML changes updates the main checkout, so the host's live bar reloads at that moment; if it renders the old layout, `touch` the changed file.

## Running the guest

```sh
cd ~/nixos-config/.worktrees/<branch>             # this session's worktree
.claude/skills/vm-test/scripts/vm-up            # boots and waits until the bar is on screen (12 s warm, ~30 s after a rebuild)
.claude/skills/vm-test/scripts/vm-switch        # apply a Nix change to the running guest (about 5 s)
.claude/skills/vm-test/scripts/vm-up --rebuild  # the reboot route: nixos-rebuild build-vm, then boot
.claude/skills/vm-test/scripts/vm-down          # power off and wait for QEMU to exit
```

- `vm-up` shares the checkout it's run from and refuses to start while a guest is running: the disk image and port 2222 are shared no matter which tree launched it. Power the guest off before launching from a different build.
- Nix changes (system, Hyprland config, user services): `git add` new files (the flake can't see untracked ones), then `vm-switch`. It builds the VM, registers the new closure in the guest's Nix database and runs the toplevel's `switch-to-configuration test` there, which also runs home-manager activation and reloads Hyprland. Only kernel, initrd or mount changes need the reboot route (`vm-down`, `vm-up --rebuild`). The qcow2 keeps the guest's home and store overlay across reboots, so windows are gone but settings persist.
- QML changes: `vm-qs restart`. inotify doesn't cross 9p, so the guest's Quickshell won't reload on its own. The script clears systemd's start limit first (a config error that crashes the shell a few times trips it), waits for "Configuration Loaded" or the load error, and prints it.
- The guest can't exercise the Intel driver, backlight, battery, Wi-Fi, Bluetooth or suspend. fprintd, tailscale, fwupd, Bluetooth, Flatpak and the desktop portals are turned off in it, and the tailscale tray applet and the ScreenSaver inhibit bridge aren't started. So portal-backed things (screen sharing, the portal's file chooser) can't be tested there, and Quickshell's "Failed to register with host portal" warning is expected in the guest. hypridle is off too, so a guest left idle never dims, locks or suspends; idle behaviour can't be tested there, though hyprlock still runs when started by hand.
- The QEMU window opens on the host's special workspace `special:vm` (SUPER+SHIFT+M); the guest display is 1920x1200 at scale 2, like the laptop, so pixel measurements carry over.
- The guest's GPU has two heads. The second (`Virtual-2`) starts out disconnected and is plugged and unplugged with `vm-display` (below), which is how multi-monitor and dock behaviour gets tested. It appears to the right of `Virtual-1`, so its coordinates start at x = 960; `grim -o Virtual-2` screenshots it, and in the QEMU window it's a second tab.

## Looking at the result

```sh
S=.claude/skills/vm-test/scripts
$S/vm-exec hyprctl clients -j                   # any command, inside the Hyprland session environment
$S/vm-exec 'hyprctl dispatch "hl.dsp.exec_cmd(\"kitty --title test\")"'   # open a test window
$S/vm-qs log 40                                 # Quickshell log, minus the guest's hardware noise
$S/vm-shot <scratchpad>/panel.png               # the bar's own area
$S/vm-shot <scratchpad>/menu.png 0,0 500x300    # a region, logical pixels, like grim -g
$S/vm-shot <scratchpad>/full.png --full
```

- `hyprctl`, `qs`, `grim` and `wtype` need the session environment; `vm-exec` provides it. `ydotool` doesn't need it.
- Screenshots are twice the logical size. For colors, padding and alignment, decode the PNG with `python3` rather than eyeballing.
- A popup can be opened for real with the input below, or, as on the host, by temporarily setting `visible: true` on it, restarting, screenshotting, then removing the line.
- `console.log` from QML never reaches `qs log`; `console.warn` does, as `WARN qml:` lines. Remove them before landing.

## Driving input

```sh
$S/vm-pointer move 60 19       # jump to logical (60, 19); exact, the guest's pointer has a flat profile
$S/vm-pointer hover 60 19      # jump and wait for a tooltip or popup to open
$S/vm-pointer nudge 35 0       # relative move; HoverHandlers follow it
$S/vm-pointer click            # left click at the current position (or: click right)
$S/vm-pointer where            # hyprctl cursorpos
$S/vm-type htop                # type into the focused window
$S/vm-type -k Return           # press a key (wtype -k names)
$S/vm-display plug             # connect the second display, as a dock would
$S/vm-display unplug           # disconnect it; its workspaces move to Virtual-1
$S/vm-display list             # connectors and Hyprland's monitors
```

- Click only where you've just seen the target. Take coordinates from a screenshot of the exact state you're about to click in, or from geometry the guest reports (`hyprctl layers -j` for a menu's surface), never from memory or from a screenshot of a different state: a menu with other entries, other row heights or the bar on the other edge puts things elsewhere. Clicks measured this way have landed; estimated ones have hit Restart instead of Log out, and a list's delete button from a screenshot of another list landed outside the menu.
- Check each step before the next. After a click or key, confirm the result you expected (the menu's layer surface present or gone, the history count, the clipboard's contents) before sending more input, and stop on anything unexpected rather than pressing on. Keys sent after an unnoticed misclick go wherever the focus ended up: a Tab and Enter after hitting Restart by mistake could have confirmed a reboot. A test that only checks an outcome can also pass for the wrong reason: typing into a launcher that never opened ran the same command in a terminal.
- Have test scripts check their own assumptions before clicking, e.g. that the bar is on the edge the coordinates expect (from `hyprctl layers -j`). A script that edits and restores a file must `vm-qs restart` afterwards, or the guest keeps the edited version (see below).

- Hyprland binds that depend on a held modifier (ALT+Tab, SUPER taps) need ydotool with raw keycodes, pressed and released explicitly, so the modifier can stay down across separate calls: `vm-exec 'ydotool key 56:1 15:1 15:0'` holds ALT and taps Tab, `ydotool key 56:0` lets ALT go. Codes: ALT 56, Tab 15, SHIFT 42, Escape 1, SUPER 125, Print 99. Binds fire from ydotool keys even while slurp has the keyboard.
- A bind can be tried at runtime without a rebuild: `hyprctl dispatch` evaluates its argument as Lua, so `hyprctl dispatch '(function() hl.bind("ALT + Alt_L", hl.dsp.exec_cmd("touch /tmp/x"), { release = true }) return hl.dsp.no_op() end)()'` registers a bind until the next reload. Have each variant touch its own file to see which ones fire.
- Allow for the UI's own delays before screenshotting: tooltips and the workspace list open after 500 ms, which `hover` already covers.
- A surface that maps under a pointer that hasn't moved since gets no pointer events from Hyprland: no hover, and clicks go to whatever was under the pointer before. So before clicking a notification popup (or any surface that appears on its own), wait until it has mapped, then move the pointer onto it, or `nudge 1 0` if it's already there, and only then click. Poll `hyprctl layers -j` for the surface rather than sleeping a guessed time: a screenshot notification's popup maps about 1.7 s after the key, and a move made before that counts for nothing. A real mouse always moves first, so this only bites scripted tests. Checking `vm-qs log` for new debug lines is also easy to misread: `vm-qs log N` shows the last N lines whether or not they're new, so tag each run's `console.warn` output (an id or counter) to tell runs apart.
- `vm-pointer move` and `hover` use `ydotool mousemove --absolute`, which first slams the pointer into the top-left corner and then moves it, so the pointer crosses the bar on the way. That counts as the shell having received input, which can hide bugs that only show before any input (a Wayland popup grab, for one, is refused until then). To keep the pointer off Quickshell's surfaces, use `nudge` only.
- Menus that take the keyboard (`KeyboardMenu`: the launcher, clipboard and network menus) are layer surfaces, so they open on a fresh boot with no prior input. Hyprland gives such a layer the pointer as well as the keyboard when it maps, wherever the cursor is; `KeyboardMenu` maps it as Exclusive and drops to OnDemand 50 ms later, which makes Hyprland re-evaluate pointer focus. To test that, click the bar twice without moving the pointer: the second click must reach the bar.
- Don't test hover through the QEMU window's own pointer or QMP `input-send-event`: both drive QEMU's usb-tablet, and the guest only delivers that device's enter, leave and clicks to Quickshell, not motion within a surface, so a HoverHandler never sees the pointer slide from one item to the next. `hl.dsp.cursor.move` warps the cursor without producing hover events at all. ydotool is a real uinput mouse and has none of these problems.
- The guest's clock is in UTC, not the laptop's time zone, so anything clock-based (the night light schedule) sees different local times there. Open-Meteo answers in the location's own time zone (`timezone=auto`). To test time-based logic without waiting, temporarily bind the event time to "a couple of minutes from now" (`{ const d = new Date(); return d.getHours() * 60 + d.getMinutes() + 2 }`), shorten durations and timer intervals, and watch `hyprctl hyprsunset temperature` (or `console.warn` lines) in a loop. hyprsunset keeps reporting the last temperature after `identity`.
- The guest has no battery, so the battery indicator and its tooltip can't be exercised there.
- Battery logic can still be tested by temporarily replacing the UPower-derived properties (`percent`, `discharging`) with plain properties stepped by a `Timer`, logging each step with `console.warn`. `Quickshell.reload(false)` from such a timer (guarded by a `PersistentProperties` flag so it fires once) tests reload behaviour, since the guest's shell doesn't reload on file changes.
- The guest has no sound card, so `modules/vm.nix` gives it null audio devices that discard what's played: Speakers (the default), Headphones (`device.form-factor=headphone`, for the bar's headphones icon) and a Microphone. `vm-exec 'wpctl set-default <id>'` switches outputs (ids from `wpctl status`); `wpctl set-volume @DEFAULT_AUDIO_SINK@ 0.4` brings up the OSD. WirePlumber remembers a default you set across reboots (in `~/.local/state/wireplumber/default-nodes`), so switch back to Speakers when done.
- For a media player (the MPRIS player behind the media controls), `$S/vm-media start` plays a looping sine tone in mpv, which has the MPRIS plugin on the host and in the guest; `vm-media pause`, `play`, `status` and `stop` drive it.
- The guest has no backlight or Bluetooth adapter, so sections that hide without them don't appear. To check their layout, temporarily replace the visibility conditions (and the backlight's `current`/`max`) with constants, restart, screenshot, then restore the files.
- Animations (150 ms, `Theme.animationDuration`) finish before a `vm-shot` taken from the host can land, since each ssh call takes longer than that. To catch one mid-way, click and capture in a single guest command and copy the frames back: `vm-exec 'mkdir -p /tmp/f; ydotool click 0xC0; for i in 1 2 3 4; do grim -g "620,180 340x320" /tmp/f/$i.png; done'`, then `scp 'vm:/tmp/f/*.png' <scratchpad>/`. Each grim takes about 100 ms, so only the first frame or two land inside the animation, and a glitch lasting a frame or two slips between them. To check smoothness, record at 60 fps instead: `nix build --no-link --print-out-paths --inputs-from . nixpkgs#wf-recorder` on the host (the guest sees the store path), then in one `vm-exec` start `<path>/bin/wf-recorder -g "<region>" -r 60 -f /tmp/r.mkv` in the background, click with ydotool, `pkill -INT wf-recorder`. Copy the file back, decode it with `ffmpeg -vf format=gray -f rawvideo` and track a landmark's row per frame in python. That's how menus were found jumping by the size change for a few frames while their popup window resized every frame (fixed by `DropdownMenu` keeping one window height while open).
- For a change that shouldn't alter the look (a refactor), screenshot the same menus before and after and diff them with ImageMagick (`magick a.png b.png -compose difference -composite -trim -format %@ info:`). Two runs without changes come out pixel-identical, but mask the clock, and expect live data such as the weather to differ.
- Notifications can be posted and closed from the shell with `busctl --user call -- org.freedesktop.Notifications ...`. The `--` is needed: without it busctl reads an `expire_timeout` of `-1` as an option. `notify-send` isn't on the guest's PATH; take libnotify's store path from a script that has it in `runtimeInputs` (grep the script for `libnotify`). Its `-i` lands in the `image-path` hint, not in `app_icon`, so Quickshell sees an empty `appIcon` for it.
- `vm-qs restart` restarts the service, which empties the notification history and every `PersistentProperties`; only a QML reload keeps them. To test what survives a reload, use the `Quickshell.reload(false)` timer trick above, then wait past its interval before looking.
- The scripts packaged in `home/hyprland.nix` and bound in `home/hypr/binds.lua` (`screenshot-window`, ...) aren't on PATH either; take their store paths from `~/.config/hypr/nix.lua`. Start one that leaves a process behind (`notify-send -A` waiting for its button) with `setsid -f <script> >/dev/null 2>&1`, or the ssh call hangs until that process exits.

## What has been measured and tried

- A warm boot takes 12 s to the bar (kernel and initrd 3.5 s, system services 3.6 s, greetd at 7 s, Quickshell starts at 8.5 s and finishes loading at 10 s). Right after a rebuild it can take 30 s or more, because the new store paths aren't in the host's page cache yet. Boot isn't CPU or memory bound (4 cores and 8 GB are mostly idle), it's 9p latency.
- `virtualisation.msize` at 512 KiB (from the 16 KiB default) took about 0.8 s off Quickshell's config load. `cache=loose` on the config share took a further 0.3 s but makes worktree edits invisible to the guest, so it's not used. Turning off the portals, Flatpak and the inhibit bridge saved another 0.3 s. Faster polling in `vm-up` saved nothing: the lag after the bar appears is QEMU's own startup plus one ssh round trip.
- Paths built on the host after the guest booted exist in the guest's store but aren't valid in its Nix database, which only registers the closure it booted from. Anything that calls `nix-store --realise` or `nix path-info` on them fails, and home-manager's activation does exactly that, silently. `vm-switch` copies the closure's database entries over first (`nix-store --dump-db` on the host, `--load-db` as root in the guest, via a file because `sudo -S` reads stdin).
- A snapshot of a booted guest isn't an option: QEMU can't save a guest using virgl GL, which Hyprland needs.
- Display hotplug: QEMU marks a virtio head enabled only once its GTK tab has a surface, so `max_outputs=2` alone leaves `Virtual-2` disconnected. Writing `on` or `off` to `/sys/class/drm/card0-Virtual-2/status` (as root) forces the connector and re-probes it, but raises no hotplug event; `udevadm trigger --action=change /sys/class/drm/card0` supplies the event, and Hyprland then adds or removes the monitor through its normal path. (Writing `detect` to that file clears the force, and the debugfs `force` file alone doesn't re-probe.) Hyprland gives a new monitor workspace *index + 1* when no workspace rule says otherwise, taking it from the other monitor, windows included: plugging a second display grabs workspace 2.

- Hyprland config can be tried at runtime the same way as a bind: `hyprctl dispatch '(function() hl.layer_rule({ match = { namespace = "quickshell" }, blur = true, blur_popups = true, ignore_alpha = 0.2 }) return hl.dsp.no_op() end)()'` adds a layer rule until the next reload, and `hl.config({ decoration = { blur = { size = 8 } } })` inside the same wrapper changes an option. An unknown field is reported as an error, so it's also a quick way to check a rule's field names.
- Comparing looks: a Python script that rewrites option lines in `Theme.qml`, runs `vm-qs restart`, clicks an indicator with `vm-pointer` and takes a `vm-shot --full` per variant captures a dozen designs unattended (each takes about 15 s). `pkill kitty` in the guest shows the wallpaper behind menus; a terminal full of `ls --color` output is a good dark backdrop otherwise. The host has ImageMagick but no Pillow; `nix-shell -p python3Packages.pillow` has it for stitching the shots into a labelled grid.
- Flatpak: to test anything that uses it, comment out the `services.flatpak.enable` and `xdg.portal.enable` overrides in `modules/vm.nix` for the session (don't commit that) and `vm-up --rebuild`. Over ssh you're not an active local session, so polkit refuses remote and install changes; run those with `sudo` (`flatpak remote-add ... flathub`). For a real pending update, install a small app and pin it to an older commit: Flatseal (about 1 MB, plus the GNOME runtime) with `flatpak update --commit=<parent from flatpak remote-info --log flathub com.github.tchx84.Flatseal>`. A bogus remote URL doesn't make `flatpak update` fail: it treats fetch errors as non-fatal and exits 0, so fake a failure by swapping the command instead. The installed apps persist in the qcow2.
- Hyprland crashed once (SEGV in `CPopup::coordsRelativeToParent` from `mouseMoveUnified`) when Quickshell was restarted with a menu open; repeating it didn't reproduce. If the bar's log suddenly shows "Unable to connect to hyprland event socket", look in `~/.cache/hyprland/` for a crash report and run `vm-qs restart` again.

- Idle inhibitors: the ScreenSaver inhibit bridge isn't started at boot but its unit exists, so `systemctl --user start screensaver-inhibit` brings it up for a test. `mpv --force-window=immediate --loop=inf av://lavfi:testsrc` (start it with `setsid -f`) plays a test pattern and holds a Wayland idle inhibitor, which `hyprctl clients -j` shows as `inhibitingIdle`; `systemd-inhibit --list` shows the logind ones. hypridle is off, so this checks who holds what, not whether the screen would dim.
- Quickshell's process is named `.quickshell-wra` (the wrapper's truncated name), so `pkill -x quickshell` matches nothing; use `pgrep -x .quickshell-wra`. And never `pkill -f` a pattern that appears in the same `vm-exec` command: it matches the remote shell running that command and kills the ssh call (exit 255).

- Logging out (SUPER+M or the start menu) ends Hyprland and greetd starts it again through `default_session`, which greetd counts as a greeter. A second log out ends that "greeter" without it having logged anyone in, and greetd then stops for good, leaving no session. `ssh vm 'echo isaiah | sudo -S systemctl start greetd'` brings the desktop back (about 6 s to the bar).
- To check that the bar runs an external command, and with which arguments, when the effect can't be seen in the guest (brightness, power), put a logging stand-in earlier on Quickshell's PATH, which starts with `~/.local/bin`: a two-line script there named like the command that appends `"$@"` to a file. Trigger the action, read the file, then delete the stand-in.
- When a script edits a file in the worktree for one test pass and restores it afterwards, the guest's shell keeps whatever it loaded last until the next `vm-qs restart` (no inotify over 9p). Restart after restoring, or later clicks aim at a layout that isn't there.

- To make the focused window fullscreen (the config has no bind for it): `vm-exec 'hyprctl dispatch "hl.dsp.window.fullscreen()"'`; the same call toggles it back. The config moves a fullscreen window to a workspace of its own (101 and up). `hyprctl layers -j` lists surfaces per level (2 = top, 3 = overlay), which shows which layer a Quickshell window is on.
- Fullscreen games: `neverball` is installed in the guest (`SDL_VIDEODRIVER=x11 neverball` runs it through XWayland). It saves its fullscreen state to `~/.neverball/neverballrc` on exit, including fullscreen set by the compositor, so check the `fullscreen` line there before each launch or a "windowed" launch comes up fullscreen. socat isn't in the guest; poll `hyprctl clients -j` to follow fullscreen and workspace changes.

- Hyprland bind behaviour, found while building the ALT+Tab switcher: a `release` bind only fires if no other key was pressed since its own key went down (which is what keeps SUPER+H from opening the launcher), unless it's `transparent`. A `catchall` bind in a submap fires on every key, alongside the bind that matches, so it can't serve as "any other key". A `hl.dsp.global` dispatched from a release bind reaches the Quickshell `GlobalShortcut` as `released`, not `pressed`.

## Keep this skill current

If you learn something new about driving the VM or testing in it (a technique that works or doesn't, a timing, a quirk of the guest, a script that would have saved repetition), add it here or to the scripts as part of the same task, in its own commit separate from the feature's. Lessons that only live in a session get lost; this file doesn't.
